## Qué es este proyecto

`onplay-core` es un sistema POS/ERP para Comercializadora y Distribuidora BM: la **fuente de verdad única** de productos, precios, inventario, clientes y ventas, por encima de dos tiendas WooCommerce existentes (onplay.cl y onplaygames.cl) que **no se reemplazan ni se fusionan**. El documento rector es `docs/01-SDD-general.md` (SDD general v1.2); la spec ejecutable de la Etapa 1 es `docs/02-SDD-etapa1-mostrador.md`.

## Comandos

- **Instalar:** `npm install` (raíz; workspaces npm)
- **Dev API:** `npm run dev` (raíz) — levanta Fastify en `:3010` con tsx watch
- **Dev web:** `npm run dev -w @onplay/web` — Vite en `:5183` con proxy `/api` → `:3010` (mismo origen para la cookie H7)
- **Build web:** `npm run build -w @onplay/web` (tsc --noEmit + vite build)
- **Build completo:** `npm run build` (raíz) — typecheck de la API + build de la web; es la puerta previa al despliegue
- **Producción:** `npm run start -w @onplay/api` (tsx; con `NODE_ENV=production` sirve también `apps/web/dist`). Despliegue: `git pull && npm ci && npm run build`, `npx prisma migrate deploy` desde `apps/api/`, `pm2 reload onplay-core` (primera vez desde `apps/api/`: `pm2 start npm --name onplay-core -- run start`)
- **Tests:** `npm test` (raíz, todos los workspaces) o `npm test -w @onplay/dominio` para uno
- **Migraciones:** desde `apps/api/`: `npx prisma migrate dev` / `npx prisma migrate deploy` / `npx prisma validate` (el schema vive en `prisma/` de la raíz; `apps/api/package.json` lo apunta vía el campo `prisma.schema`)
- **Semillas:** `npm run seed` (idempotente, upserts)
- **Admin inicial:** `npm run crear-admin -- <email> <nombre> [password]`
- **Typecheck:** `npx tsc -p apps/api/tsconfig.json --noEmit`
- **MySQL local (dev):** MariaDB de XAMPP — arrancar con `C:\xampp\mysql\bin\mysqld.exe`; base `onplay_core`, usuario `root` sin clave. `DATABASE_URL` en `apps/api/.env` (no versionado)
- **Prisma está fijado en 5.x** a propósito: el esquema de la spec usa `previewFeatures = ["fullTextIndex", "fullTextSearch"]`, que en Prisma 6+ cambian de estado. No actualizar a Prisma 6+ sin ajustar el esquema y verificar contra la spec.

## Stack y estructura prevista (SDD §5)

- **Backend:** Node.js 20 + TypeScript estricto + Fastify. **Base de datos:** MySQL 8 con Prisma (migraciones versionadas). **Frontend:** React 19 + Vite + Tailwind 3.4, un solo bundle PWA (Mostrador + Backoffice) con IndexedDB para caché offline.
- Monorepo con **npm workspaces**, sin Turborepo/Nx: `apps/api`, `apps/web`, `packages/dominio` (tipos y reglas de negocio), `packages/woo-client` (cliente tipado de WooCommerce REST v3), `prisma/`, `docs/`.
- **Despliegue:** `git pull` + `npm ci` + `prisma migrate deploy` + `pm2 reload`. Sin CI/CD por ahora.

## Principios vinculantes (SDD §3)

Existen para impedir que el proyecto muera por alcance, como cuatro intentos anteriores. **No son negociables:**

- **P1** — Cada etapa entra en producción y es útil sola. Funcionalidad no listada en la spec de la etapa actual se rechaza y se agenda (Riesgo R4).
- **P2** — Espejo antes que control: primero se *lee* de WooCommerce; solo se *escribe* (E3) cuando la lectura es confiable.
- **P3** — Ningún SKU ya publicado se renumera. La correspondencia vive en la tabla `producto_canal` (`externo_id`, `externo_sku`), no en convenciones de nombres.
- **P4** — El stock es opcional por producto (`controlaStock`, default `false`).
- **P5** — Stock, caja y saldo de cliente son libros de movimientos **append-only**; el saldo es siempre `SUM()`, nunca un campo que se sobrescribe.
- **P6** — Un proceso Node, una base MySQL. Sin microservicios, colas, event bus ni herramientas de build extra hasta que un problema medido lo exija.
- **P7** — Español en el dominio (`producto`, `venta`, `turnoCaja`), inglés en la infraestructura (`Repository`, `Service`, `Controller`).
- **P8** — Offline-tolerante en mostrador: la PWA vende con catálogo cacheado y encola las ventas.
- **P9** — Nada se borra: anulaciones y correcciones son registros nuevos que compensan.

## Reglas de seguridad S1–S4 (SDD §8.3 — de defectos reales del Binder OP)

- **S1** — Toda escritura a un canal externo tiene modo `dryRun`, que es el **valor por defecto**. El dryRun no tiene efectos colaterales (tampoco crea categorías).
- **S2** — El push de stock exige verificación previa: leer el stock del canal y compararlo con `producto_canal.stockPublicado` antes de escribir. Si no coincide, **no se escribe**: se reporta como discrepancia. (La API `wc/v3` solo acepta `stock_quantity` absoluto.)
- **S3** — Ningún secreto llega al navegador. Credenciales de WooCommerce (`ck_`/`cs_`) solo en variables de entorno del servidor; auth por JWT + cookie. Nunca `VITE_*` con credenciales.
- **S4** — Toda escritura de datos es transaccional (MySQL). Nunca persistir estado en JSON a disco.
- **Tests desde el primer commit** para reglas de negocio: cálculo de total, arqueo de caja, generación de SKU, validación de pagos.

## Convenciones de código y datos

- **Prisma/MySQL en `camelCase`**, sin `@map` (el SDD documenta en `snake_case` solo por legibilidad: `precio_venta` ↔ `precioVenta`).
- **IDs:** `cuid` de Prisma en todas las entidades. Excepción: `idempotencyKey` de `venta` es un ULID generado por el cliente.
- **Precios en CLP como `int`**, sin decimales.
- `producto.juego` es **string libre, no enum** (juegos nuevos aparecen varias veces al año). `producto.tipo` sí es enum. Atributos específicos de tipo van en `atributos` JSON, no en columnas.
- **SKU maestro:** `{PREFIJO_TIPO}-{IDENTIFICADOR}` (`MTG-`, `OPT-`, `SLD-`, `ACC-`, `SNK-`, `JDM-`, `EVT-`). Es interno; **no se publica** en E1 y nunca reescribe un SKU existente en WooCommerce.
- **Folios** (`V-2026-00001`) se asignan con `SELECT ... FOR UPDATE` sobre la tabla `correlativo`, dentro de la misma transacción de la venta.
- Sincronización: lotes de 50, upsert por `externo_id` (llave secundaria `externo_sku`), un error por ítem nunca aborta el lote, todo se registra en `sync_log`. `auditoria` (acciones humanas) y `sync_log` (acciones de máquina) son tablas **distintas** — no mezclarlas.
- Ninguna venta se registra sin `turno_caja` abierto. Una venta de un turno cerrado no se anula (se resuelve con devolución en E2). El arqueo incluye `monto_apertura` y excluye ventas anuladas.
- Entidades por etapa (SDD §6.2): ninguna tabla se crea antes de la etapa que la necesita (`ubicacion`/`movimiento_stock` en E2; `cliente`/`movimiento_monedero` en E4; `costo_referencia` por migración en E6).

## Roadmap y dependencias (SDD §9)

E1 (mostrador: precio + venta + caja) → E2 (inventario) → E3 (sync bidireccional) y E6 (compras/márgenes); E4 (cliente/monedero, depende solo de E1) → E5 (eventos). En E3 no se avanza de subetapa (precio → stock → pedidos) hasta que la anterior corra 7 días sin discrepancias. Staging obligatorio desde E3.

## Sistemas existentes que NO se tocan

- **Binder OP** (Node + Puppeteer) y **plugin OnPlay Binder** (CSV + Scryfall) siguen siendo los cargadores de catálogo de cartas hacia onplay.cl; `onplay-core` los consume vía el pull de E1.
- El checkout de los sitios (Transbank, Mercado Pago, carrito Woo) sigue tal cual.
- Fuera de alcance: facturación electrónica SII, fusión de canales, grading/variantes foil en E1–E3.
